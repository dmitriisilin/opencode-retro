# opencode-retro

[English](README.md) | [Русский](README.ru.md) | [简体中文](README.zh-CN.md) | [Español](README.es.md) | **日本語**

> `README.md` の翻訳です。英語版が正本（canonical）であり、内容が食い違う場合は英語版が優先されます。

コーディングエージェントのための振り返りツール。セッション中の摩擦を、プロジェクト自身のハーネス、すなわちそのスキル、指示書、ツールへの変更案に変える [OpenCode](https://opencode.ai) v2 プラグインです。

エージェントは自分のセッションから学びません。どこでつまずいたかを示す記録はログだけであり、そのログは読まれないままになります。このプラグインがログを読み、提案を持って戻ります。

> 状態: 実装は完了して動作しますが、まだ未リリースです。OpenCode 2.0.32 上で検証済み。npm パッケージは現時点でプレースホルダーのため、インストールはパス指定で行います。

## 解決したい問題

同じ障害がセッションごとに繰り返されます。

- あるスキルがリンターの実行を指示する。しかしプロジェクトにリンターはない。エージェントはそれでも実行し、四十個のファイルを書き換え、気づいて、すべてを巻き戻す。
- 失敗するコマンドが数回再試行されるが、試行の間に何も変わっていない。
- 計画中のタスクが「今は不可能」として静かに取り下げられる。
- 同じ訂正が三週間続けて手作業で与えられる。
- 二十ステップを節約できたはずのツールが、そもそも存在しない。

これらはすべてログの中にあります。そしてどれも次のセッションには届きません。

## 仕組み

意図的に分けられた二つのループがあります。前者は自動で進み、注意を必要としません。後者は要求に応じて動き、一度に一つの判断を生みます。

### 収集

すべてのツール呼び出しとすべてのプロンプトが、シャドーログ `.retro/sessions/<id>.jsonl` に追記されます。モデルは関与せず、プラグインは書き込むだけです。そのためこのログはコンテキストの圧縮から独立しており、セッションが自身の履歴をどう扱っても、生の軌跡は残ります。

セッションが終わるとキューに入ります。次のセッションの最初のプロンプトが、クリーンなコンテキストでのモデル呼び出し一回でそのキューを清算します。作業を行ったエージェントは意図的に使いません。自分の判断を弁護してしまうからです。

この呼び出しが受け取るのは、セッションの圧縮された像です。ツールの出力は刈り込まれ、プロンプトと応答はそのまま保たれます。答えるのは一つの問いだけです。

> このセッションをもう一度実行するなら、より短く、より真っ直ぐ進むためにプロジェクトの何を変えるべきか。

その答えが `.retro/lessons/` に置かれる教訓の一覧です。

教訓は一セッション遅れて現れます。二度と開かれないプロジェクトには何の費用もかからず、`/retro` は要求に応じてキューを清算します。

### 抽出が何を手がかりにするか

判断基準はプラグインに組み込まれていません。読んで編集できるファイル `.retro/prompts/extract.md` に置かれ、探す価値のある形を記述します。

- 無駄に終わった作業。同じ呼び出しが繰り返され、その間にどのファイルも変わっていない。
- いったん行われ、その後取り消された編集。後の編集によるものでも、作業ツリーを破棄したことによるものでも同じです。
- 行き止まりまで付き従ったスキル。そのスキルが指示したコマンドが、あとで失敗した場合です。
- 失敗に見えない失敗。「completed」と読めるステータスの裏にある、ゼロでない終了コード。
- 静かに取り下げられたタスク。エージェントが書いた文章の中にしか現れません。
- ユーザーが二度以上与えざるを得なかった訂正。

このファイル自身に、これは出発点でありチェックリストではないと書かれています。

### レビュー

ログを読むのはプラグインで、提案を読むのは人です。プラグインは提案で止まり、プロジェクトのファイルは編集しません。

| コマンド | 動作 |
|---|---|
| `/retro` | 教訓を一つ渡します。未決のもののうち最もスコアの高いものです。 |
| `/retro auto` | 待機中のすべての教訓を一つの計画として渡し、一度で承認できるようにします。 |
| `/retro check` | プラグインが機能しているかどうかを報告します。 |

教訓は、そのコマンドを実行したセッションに、すでにそこにいるエージェント宛で届きます。まずその教訓がまだ成り立つかを判断するよう求め、次にそれを伝えるよう求め、判断が下るまで何も変更しないよう求めます。

```
# retro — lint-skill-no-config

lint スキルは `npx eslint . --fix` を指示しているが、このプロジェクトでは実行できない。

2 セッションで確認、9 ステップを消費、確信度 0.9、スコア 16.2。
最後に見られたのは 3 セッション前。

提案する変更
  AGENTS.md — lint の要求を、コミット済みの ESLint 設定がある場合に限る条件付きにする。

判断が必要
  このプロジェクトは ESLint を設定すべきか、それともこの約束事をやめるべきか。
```

判断は、そのセッションにいる人とエージェントのものです。エージェントはファイル、履歴、そしてプロジェクト自身のスキルを持っており、その教訓が今も当てはまるかを判断する役としてはプラグインより適しています。判断が下ると、エージェントは `retro_decide` ツールでそれを記録します。このツールは帳簿をつけるだけです。却下は記憶され、その教訓は再び提案されません。

`/retro auto` は、同じ引き渡しを一度にまとめて行うものです。待機中の教訓が順位づけされ、まだ成り立つものがファイル単位でまとめられた一つの計画になり、その計画が一度だけ承認されます。

### 修正がどこに属するか

提案はスキーマではなく示唆です。よくある宛先は次のとおりです。

- スキル。その作業がこのプロジェクトで実際にどう行われるかに合わせて修正または追記します。
- `AGENTS.md` への指示。事実または制約です。
- 欠けているツール。すでに生じた損失とともに依頼として書き起こします。
- コード自体の変更。罠そのものを無くすためのものです。自動では適用されません。
- 以上のいずれにも当てはまらないもの。置き場所は人が決めます。

教訓そのものは常に一つのワークスペースに属します。教訓とは一つのプロジェクトのセッションから得られた証拠であり、そのプロジェクトの中だけに存在します。

一方、修正は別の場所に属することがあります。摩擦の一部はリポジトリ固有のものです。そこに合わないスキル、そこでは真でない指示などです。別の一部は、人と一緒に移動する習慣に関わります。課題管理ツールの使い方、ブランチの命名、プロジェクトからプロジェクトへ持ち運ばれる約束事です。前者はプロジェクトのハーネスに属し、後者は `~/.config/opencode/AGENTS.md` やグローバルなスキルといった全体のハーネスに属します。

ある教訓がどちらを必要とするかは、引き渡しの時点で決まります。プラグインは推測せず、全体のハーネスを独自に編集することもありません。

## 教訓

教訓は YAML フロントマターを持つ Markdown ファイルです。

```yaml
id: lint-skill-no-config
statement: The lint skill assumes eslint; this project has no linter.
evidence:
  - session: a81f
    steps: [41, 58]
  - session: c204
    steps: [12, 19]
cost: 34
recurrence: 3
confidence: 0.9
lastSeen: 41
recordedAt: 2026-10-19T15:16:04.134Z
proposal:
  target: .opencode/skills/lint/SKILL.md
  change: |
    Before running, check for a lint config and a lint script.
    If absent, do not run; report instead.
ask: Is the linter really unused here?
status: new
```

`cost` はその問題が消費したステップ数で、セッションをまたいで合算されます。`recurrence` はそれが現れた独立したセッションの数です。`lastSeen` は最後に現れた時点でのワークスペースのセッション通算数です。

### 順位づけ

スコアは `cost × recurrence × confidence × freshness` です。

鮮度は、その問題が現れなかったセッションが十回続くごとに半減します。日数ではなくセッション数で数えます。一日一セッションの使い方では、暦で測る減衰は一晩ですべてを埋めてしまいます。

再発は、一度の高額な事故より重く扱われます。三つのセッションで見られた問題は、四つめでも見られます。

### ライフサイクル

教訓はセッションではなく問題を鍵とします。同じことに遭遇した二度目のセッションは、別のファイルを作るのではなく、証拠を加えて `recurrence` を増やします。

`lessons/` には未決の問いだけが置かれます。判断が下るとファイルは `archive/` に移り、何も削除されません。いったん閉じたあとに戻ってきた問題は、同じ問題であることに加えて、その修正が持たなかったという知らせでもあるため、履歴をそのまま保って再び開かれます。既定で三十という上限が一覧を短く保ち、あふれた分も同様に保管されます。

## これは何ではないか

- **記憶プラグインではありません。** 記憶プラグインは知識ベースを作り、エージェントはそれを参照することを覚えていなければなりません。このプラグインはハーネスがすでに読むファイルを編集します。スキルの中にある知識を思い出す必要はありません。
- **ループ破りではありません。** ループ検出器はその場でエージェントを止めます。このプラグインは次のセッションに働きかけます。どちらも役に立ちます。
- **成功の記録装置ではありません。** 自己改善型スキルのツールはたいてい何がうまくいったかを記録します。このプラグインは何がうまくいかなかったかを記録します。安価な成果はそこにあります。

## インストール

npm パッケージは現時点ではプレースホルダーのため、`opencode.json` はチェックアウトしたディレクトリを指す必要があります。パスは絶対パスでなければなりません。相対パスの場合、セッションの起動がエラーも出さずに止まったままになります。

```jsonc
{
  "plugins": [
    {
      "package": "/abs/path/to/opencode-retro",
      "options": {
        "model": { "providerID": "deepseek", "id": "deepseek-flash" }
      }
    }
  ]
}
```

`options.model` は必須です。これがない場合、OpenCode は自身の無料枠を解決しますが、プラグインはそれを使用できません。

その他はすべて任意です。ディレクトリを指定する `dir`（既定は `.retro`）、プロンプトのディレクトリを指定する `prompts`、セッション数で指定する `halfLife`（既定は十）、`/retro auto` 一回あたりの教訓数である `autoLimit`（既定は十）、そして `maxOutput`、`extractTimeoutMs`、`keepSessions`。

### ディスク上に現れるもの

プラグインが書き込むものはすべてプロジェクト内の `.retro/` 以下に収まり、提案が受け入れられた場合を除いて他の場所には書き込みません。すべてプレーンテキストです。

```
.retro/
  prompts/
    extract.md       何を教訓とみなすか
    review.md        教訓をどう引き渡すか
    review-auto.md   まとまりをどう一つの計画にするか
  sessions/          生のログ。抽出後に削除される
  lessons/           未決の問い
  archive/           判断済みと押し出された教訓
  selfcheck.md       プラグインが機能しているか
  state.json
```

ログはそのセッションが抽出された時点で削除されます。物語は教訓そのものが、ステップの範囲は証拠が担っているため、生のログに残る役目はありません。

このうち `lessons/` と `archive/` はプロジェクトについての知識であり、バージョン管理に含める価値があります。読める形式であり、レビューに現れ、リポジトリとともに移動します。残りは機械的な状態です。妥当な `.gitignore` は次のとおりです。

```
.retro/sessions/
.retro/prompts/
.retro/selfcheck.md
.retro/state.json
.retro/plugin.log
```

プロンプトがここに挙がっているのは、独自のものを固定したいプロジェクトが意図してコミットするからにすぎません。種をまかれた複製は、同梱の既定値そのものです。

### プロンプト

プラグインの振る舞いは三つのプロンプトが決め、その三つはいずれもプロジェクト内のファイルです。何を教訓とみなすか、教訓をどう引き渡すか、教訓のまとまりをどう一つの計画にするかです。

それぞれ初回実行時に同梱の既定値から種をまかれ、以後書き換えられません。解決の順序はまずプロジェクト、次に `~/.config/opencode/retro/prompts/`、最後に同梱の既定値です。そのためプロンプトは一つのプロジェクトに固定することも、すべてのプロジェクトに固定することも、どちらもしないこともできます。

新しい既定値が公開されると、`prompts/updates/<name>.vN.md` として届き、そのファイルは使用されていないという注記が冒頭に付きます。利用者に代わって適用されるものは何もありません。

ソースに残るのは機械的な部分です。パーサーが要求する出力形式、教訓のフィールドの順序、そして判断を記録せよという指示です。`/retro check` は、見たい人のために出力形式を印字します。

## 動作の確認

フックが登録できたことは何の証明にもなりません。API がもう使っていない名前で登録されたフックは、登録には成功し、その後一度も発火しません。

そのため `.retro/selfcheck.md` は、設置状況ではなく生存状況を報告します。イベントストリームが見たものと、フックが受け取ったものを突き合わせます。このファイルは自身の鮮度の規則も携えています。

> 作業が進行中であるのに `heartbeat` が数分より古い場合、プラグインは動作していません。

`/retro check` はその能動版です。プラグインと OpenCode のバージョン、プラグインが依存する API の構成、設定されたモデルが応答するか、どの層のプロンプトが有効か、そして出力形式が今も解析可能な教訓を生むかを報告します。

## 今後の計画

自律は、提案が受け入れられたか却下されたかというプラグイン自身の記録から得られるもので、あらかじめ与えられるものではありません。

| 段階 | プラグイン | 人 | |
|---|---|---|---|
| L0 | セッションを収集し教訓を抽出する | `lessons/` を直接読む | 利用可能 |
| L1 | 教訓を一つずつ提案する | エージェントと一緒に判断する | 利用可能 |
| L1.5 | 待機中のすべてを一度に計画する | 計画を一度承認する | 利用可能 |
| L2 | 確認済みの教訓をブランチに適用する | そのまとまりをレビューする | 予定 |
| L3 | スキルと指示を直接適用する | ツールとリファクタリングの依頼だけを見る | 予定 |

## 必要なもの

- OpenCode v2、`@opencode/plugin` 2.0 以降。2.0.32 で検証済み。
- 抽出用のモデル。`options.model` に明示的に指定します。安価なもので十分です。
- 実行時依存はありません。
