# opencode-retro

[English](README.md) | [Русский](README.ru.md) | **简体中文** | [Español](README.es.md) | [日本語](README.ja.md)

> `README.md` 的译文。英文版为正本（canonical）；若两者不一致，以英文版为准。

面向编码智能体的复盘工具。这是一个 [OpenCode](https://opencode.ai) v2 插件，它读取已结束会话的对话记录，找出能让智能体工作得更顺的地方，并把它们转化为对项目自身工作环境的改动建议，包括其技能、说明文件与工具。

智能体不会从自己的会话中学习。它在哪里受阻，唯一的记录就是日志，而日志通常没人看。本插件负责读日志，并带回建议。

> 状态：功能完整且可用，但尚未发布。已在 OpenCode 2.0.32 上验证。npm 包目前仍是占位，因此需通过路径安装。

## 要解决的问题

同样的障碍会在一次次会话中反复出现：

- 某个技能要求运行 linter，而项目并没有 linter。智能体照做，改写四十个文件，随后察觉，又把一切回滚。
- 说明文件要求在提交前执行构建命令，而项目并未定义这样的脚本，于是每次照办这一步都会失败。
- 代码风格没有写在任何地方，于是每次会话都要先读源码把它重新推导一遍。
- 一条失败的命令被重试数次，而两次尝试之间什么都没有改变。
- 计划中的一项任务被悄悄放下，理由是“目前做不到”。
- 同一条纠正已经连续第三周由人手动给出。

这些都在日志里，却没有一条能进入下一次会话。

## 工作方式

两个有意分开的循环。前者自行运转，不占用注意力；后者按需启动，每次给出一个决定。

### 采集

每一次工具调用与每一条提示都会追加写入影子日志 `.retro/sessions/<id>.jsonl`。此过程不涉及模型，插件只负责写入。因此该日志不受上下文压缩影响：无论会话如何处理自己的历史，原始轨迹都会保留。

### 提炼

会话结束后，它的日志会进入待分析队列。该队列在同一工作区中下一次会话的第一条提示时被处理，`/retro` 也可按需处理。

分析在任何会话之外进行：一次模型调用，输入就是那份日志，没有智能体，没有历史，也没有工具。它不触碰触发它的那次会话的上下文，也不会拖慢该会话的第一条提示。那个干过活的智能体被刻意排除，因为它会为自己的决定辩护。

默认情况下，分析使用你自己会话所用的模型。`options.model` 可以指定另一个；如果你的默认模型属于 OpenCode 的免费层，那就值得指定，因为插件不得调用它们。

该调用收到的是会话的压缩视图：工具输出经过裁剪，提示与回复保持完整。它只回答一个问题：

> 如果这次会话重新运行一遍，项目里应当改变什么，才能让它走得更短、更直？

答案是 `.retro/lessons/` 中的一份教训清单。

一次会话最多花费一次调用；而工具调用少于三次的会话不花费任何调用，因为其中可读的内容太少。不再被打开的项目根本不会被分析。

### 提炼依据什么

判断标准并未写死在插件里。它们位于 [`prompts/extract.md`](prompts/extract.md)，首次运行时作为 `.retro/prompts/extract.md` 播种到项目中，并可在那里编辑。它们描述值得寻找的形态：

- 白做的工作：同一个调用被再次发出，而两次之间没有任何文件发生变化。
- 做出又被撤销的改动，无论是被后来的编辑覆盖，还是被丢弃工作区所抹去。
- 走进死胡同的技能：该技能所规定的命令随后失败。
- 看起来不像失败的失败：非零的退出码，藏在显示为 “completed” 的状态背后。
- 被静默放弃的任务：它只体现在智能体所写的文字里。
- 用户不得不给出一次以上的纠正。

该文件中明确写着：这是一个起点，而不是检查清单。

### 复核

插件读日志，人读建议。插件到建议为止，不会改动项目文件。

| 命令 | 作用 |
|---|---|
| `/retro` | 交付一条教训，即尚未裁决者中得分最高的那条。 |
| `/retro auto` | 把所有待处理的教训作为一份计划交付，一次性批准。 |
| `/retro check` | 报告插件是否在正常工作。 |

教训会被送进执行该命令的那次会话，并写给已经在场的智能体。首先请它判断这条教训是否仍然成立，然后转述，并且在作出决定之前不做任何改动。

```
# retro — lint-skill-no-config

lint 技能规定运行 `npx eslint . --fix`，而本项目无法执行该命令。

出现于 2 次会话，为此花费 9 步，置信度 0.9，得分 16.2。
上次出现在 3 个会话之前。

建议的改动
  AGENTS.md —— 将 lint 要求改为以仓库中已提交的 ESLint 配置为前提。

需要决定
  本项目是否应当配置 ESLint，还是应当放弃这条约定？
```

决定属于该会话中的人与智能体。智能体掌握文件、历史以及项目自身的技能，因此在判断一条教训是否仍然适用这件事上，它比插件更可靠。决定作出之后，智能体通过 `retro_decide` 工具记录结果。该工具只做记账：被否决的教训会被记住，不再重复提出。

`/retro auto` 是同一种交付，只是一次面对全部。待处理的教训会被排序，其中仍然成立的被汇成一份按文件分组的计划，整份计划一次批准。

### 修改应落在何处

教训记录的是问题。在何处修改，则在交接时决定：由智能体与人一起，先看清这个工作区实际拥有什么——此处工作环境会读取哪些说明文件、项目级或全局是否存在技能、是否已有更具体的东西覆盖了这项任务。

可选的做法：

- 修改说明文件，适用于广泛生效的事实或约束。
- 修改技能，当某个技能给出了错误的步骤，或在不该触发时触发。
- 新建技能，或新建一个限定于规则实际生效目录的说明文件，当合适的位置尚不存在时。
- 请求一个工具，当缺的是能力而不是说明。
- 改动项目代码，当陷阱就在代码里。未经明确同意绝不应用。
- 暂不归位，当正确的归属确实不清楚时。

教训本身始终属于单一工作区。修改则不一定：如果原因在于此人在任何地方的工作方式，那么修改属于其全局工作环境，因为只在一个项目里修好会让其余项目仍然坏着。项目之外的任何内容都不会在未经询问的情况下被改动。

具体做法与这份清单位于 [`prompts/review.md`](prompts/review.md)，它会被播种到项目中并可在那里编辑。

## 教训

一条教训是一个带 YAML frontmatter 的 Markdown 文件。

```yaml
id: lint-skill-no-config
statement: The lint skill assumes eslint; this project has no linter.
evidence:
  - session: a81f
    steps: [41, 58]
  - session: c204
    steps: [12, 19]
cost: 34
recurrence: 3
confidence: 0.9
lastSeen: 41
recordedAt: 2026-10-19T15:16:04.134Z
proposal:
  target: .opencode/skills/lint/SKILL.md
  change: |
    Before running, check for a lint config and a lint script.
    If absent, do not run; report instead.
ask: Is the linter really unused here?
status: new
```

`cost` 是该问题消耗的步数，跨会话累加。`recurrence` 是它出现过的独立会话数。`lastSeen` 是它最近一次出现时该工作区的会话计数。

### 排序

得分为 `cost × recurrence × confidence × freshness`。

新鲜度每经过十个该问题未再出现的会话便减半，并且按会话计数而非天数计算。若一天只有一次会话，按日历衰减会在一夜之间把一切埋没。

复发比单次昂贵的事故更有分量。在三次会话中出现过的问题，在第四次仍会出现。

### 生命周期

教训以问题为键，而不是以会话为键。第二次会话遇到同一件事时，只会补充其证据并把 `recurrence` 加一，而不是另建文件。

`lessons/` 只保存尚未裁决的问题。作出决定会把文件移入 `archive/`，并且任何内容都不会被删除。一个关闭后又回来的问题，是同一个问题，外加“此前的修法没有奏效”这一新情况，因此它会带着完整历史重新打开。上限默认为三十，用来保持列表简短；超出的部分同样进入归档。

## 安装

npm 包目前仍是占位，因此 `opencode.json` 应指向一份检出。该路径必须是绝对路径；相对路径会使会话启动一直挂起，且不报任何错误。

```jsonc
{
  "plugins": [
    {
      "package": "/abs/path/to/opencode-retro",
      "options": {
        "model": { "providerID": "deepseek", "id": "deepseek-flash" }
      }
    }
  ]
}
```

`options.model` 为选填。不填时，插件会使用你会话所用的模型；若尚未见到，则退回到工作区的默认模型。如果该默认模型属于 OpenCode 的免费层，请显式指定一个，因为插件不得调用这些模型。`/retro check` 会报告实际使用了哪个模型以及它来自哪里。

其余均为可选：`dir` 指定目录，默认 `.retro`；`prompts` 指定提示目录；`halfLife` 以会话计，默认十；`autoLimit` 为单次 `/retro auto` 中的教训数量，默认十；以及 `maxOutput`、`extractTimeoutMs`、`keepSessions`。

### 磁盘上会出现什么

插件写入的一切都留在项目的 `.retro/` 之下，除接受建议的情形外不会写到别处。全部为纯文本。

```
.retro/
  prompts/
    extract.md       什么算作一条教训
    review.md        一条教训如何交接
    review-auto.md   一批教训如何成为一份计划
  sessions/          原始日志，提炼后即删除
  lessons/           尚未裁决的问题
  archive/           已裁决与被挤出的教训
  selfcheck.md       插件是否在工作
  state.json
```

一份日志在其会话被提炼之后即删除。故事由教训本身承载，步数区间由证据承载，原始日志已无更多可提供。

其中 `lessons/` 与 `archive/` 属于关于项目的知识，值得提交到版本库：它们可读、会出现在代码评审里，并且随仓库一同流转。其余属于机器状态。一份合理的 `.gitignore`：

```
.retro/sessions/
.retro/prompts/
.retro/selfcheck.md
.retro/state.json
.retro/plugin.log
```

提示文件列在其中，只是因为想固定自己提示的项目会有意识地提交它们；播种出来的副本不过是随包的默认值。

### 提示文件

插件的行为由三个提示决定，三者都是项目内的文件：什么算作一条教训、一条教训如何交接、一批教训如何成为一份计划。

每个提示在首次运行时由随包的默认值播种，之后不再被写入。解析顺序为先项目，再 `~/.config/opencode/retro/prompts/`，最后是随包默认值，因此一个提示可以为某一个项目固定、为所有项目固定，或都不固定。

当更新后的默认值发布时，它会以 `prompts/updates/<name>.vN.md` 的形式出现，文件开头注明该文件并未被使用。不会有任何内容代替用户被应用。

留在源代码中的是机械部分：解析器所要求的输出格式、教训字段的顺序，以及记录决定的指示。`/retro check` 会为需要查看的人打印输出格式。

## 确认它在工作

钩子注册成功并不能证明任何事。以 API 中已不存在的名称注册的钩子，会注册成功，然后永远不触发。

因此 `.retro/selfcheck.md` 报告的是存活状况而非安装状况：它把事件流所见与钩子所收到的内容相互对照。该文件自带过期规则：

> 如果工作正在进行，而 `heartbeat` 已超过几分钟，则插件没有在运行。

`/retro check` 是其主动版本。它报告插件与 OpenCode 的版本、插件所依赖的 API 构成、所配置的模型是否响应、当前生效的是哪一层提示，以及输出格式是否仍能产出可解析的教训。

## 运行要求

- OpenCode v2，`@opencode/plugin` 2.0 或更新版本。已在 2.0.32 上验证。
- 一个插件可以调用的模型。默认使用你自己会话的模型；低成本模型即可。
- 无运行时依赖。
